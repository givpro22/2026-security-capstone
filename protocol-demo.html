E2EE 프로토콜 비교 — 전송 메시지 시각화

같은 시나리오: Alice ↔ Bob, 메시지 3개 주고받기. 각 프로토콜이 실제로 무엇을 와이어로 전송하는지 비교

ephemeral key (e) static key (s) DH 결과 (ee, es, ...) ciphertext MAC/tag 파생 키 (RK/CK/MK)

① Static X25519 (현재 구현)

libsodium crypto_box

사용자마다 X25519 키쌍 한 개. 핸드셰이크 없음. 매 메시지마다 random nonce + ciphertext만 전송.

Alice → Server → Bob1
{
  ciphertext: "7Hk2vR…+16B tag",
  nonce: "aB1C…(24B)"
}
Bob의 정적 공개키 + Alice 정적 개인키로 crypto_box. 매번 같은 키 사용.
서버는 누가 누구에게 보냈는지 + 길이 + 정확한 시각을 봄. 본문은 못 봄.
Bob → Server → Alice2
{
  ciphertext: "9Lp4zM…+16B tag",
  nonce: "qF7H…(24B)"
}
답장도 동일 구조. 두 사람 다 같은 정적 키 쌍을 영원히 재사용.
Alice → Server → Bob3
{
  ciphertext: "3Xc8tN…+16B tag",
  nonce: "mP2Q…(24B)"
}
⚠ Alice의 정적 개인키가 1년 후 유출되면 → 지금까지 저장된 모든 ciphertext 복호화 가능 (Forward Secrecy 없음)
Alice의 상태
static_priv = priv_A (불변)
static_pub = pub_A (불변)
key rotation 없음 · session 없음

② Noise XX (상호 인증 + FS)

Noise_XX_25519_ChaChaPoly_SHA256

1.5 RTT 핸드셰이크로 ephemeral 키 교환. 이후 transport 메시지는 헤더 없이 ciphertext만. 정적 키는 핸드셰이크 안에서 암호화되어 전달됨.

HS msg 1: Alice → Bob1
e_A (32B ephemeral pub)
— payload는 비어있음 —
Alice가 일회용 ephemeral 키쌍 생성. 공개키만 평문으로 전송.
HS msg 2: Bob → Alice2
e_B (32B)
ee = DH(e_A, e_B) → ck 갱신
enc(s_B) (32B + 16B tag) ← Bob의 정적키를 암호화
es = DH(e_A, s_B) → ck 갱신
enc(payload) + 16B tag
e_B는 평문이지만 s_B는 ee로 파생된 키로 암호화 → 도청자는 Bob의 정체를 모름.
HS msg 3: Alice → Bob3
enc(s_A) (32B + 16B tag) ← Alice 정적키
se = DH(s_A, e_B) → ck 갱신
enc(payload) + 16B tag
핸드셰이크 종료. 양쪽 모두 k_send / k_recv 도출 완료.
Transport 1: Alice → Bob4
enc_k_send("hi Bob") + 16B tag
nonce = counter (헤더에 없음, 둘 다 카운트)
헤더 없음. counter는 양쪽이 동기화. 매우 가벼움.
길이 + 메타데이터. 본문/정적키 모두 비공개.
Transport 2: Bob → Alice5
enc_k_recv("hi Alice") + 16B tag
✓ 세션 종료 후 ephemeral 키 폐기 → 정적키 유출돼도 이 세션 메시지는 복호화 불가 (Forward Secrecy)
세션 상태 (양쪽 동일)
ck (chaining key) ← ee, es, se 누적
k_send, k_recv = HKDF(ck)
세션 종료 시 ephemeral 폐기 → FS

③ Signal (X3DH + Double Ratchet)

X3DH + DR (WhatsApp, Signal)

비동기 시작(상대 오프라인 OK) + 메시지마다 키 갱신. 헤더에 새 ephemeral 공개키와 counter가 들어가 PCS(Post-Compromise Security) 제공.

X3DH: Alice가 서버에서 Bob 번들 fetch1
prekey_bundle = {
  IK_B (identity pub),
  SPK_B (signed prekey) + Sig_IK_B,
  OPK_B (one-time prekey)
}
Bob이 미리 서버에 올려둔 키 묶음. Bob은 오프라인이어도 됨.
Initial: Alice → Bob (first msg)2
{
  IK_A (32B),
  EK_A (32B ephemeral),
  OPK_B_id (어떤 OPK 썼는지),
  header: { DH_A0, n=0, pn=0 },
  enc(MK_0, "hi Bob") + tag
}
SK = KDF( DH(IK_A,SPK_B) ‖ DH(EK_A,IK_B) ‖ DH(EK_A,SPK_B) ‖ DH(EK_A,OPK_B) )
→ 4번의 DH로 root key 도출
Bob → Alice (응답 = 새 DH ratchet)3
{
  header: { DH_B0, n=0, pn=1 },
  enc(MK'_0, "hi Alice") + tag
}
Bob이 새 ephemeral DH_B0 생성 → RK, CK 한 단계 진행 (DH ratchet 발동).
Alice → Bob (같은 ratchet)4
{
  header: { DH_A1, n=0, pn=1 },
  enc(MK''_0, "어떻게 지내?") + tag
}
Alice가 다시 새 DH_A1 → 또 한 번 DH ratchet. 매 turn마다 root key가 바뀜.
Alice → Bob (연속 발송)5
{
  header: { DH_A1, n=1, pn=1 },
  enc(MK''_1, "잘 지내?") + tag
}
같은 DH ratchet이지만 symmetric ratchet으로 CK → CK', MK 새로 도출.
MK는 매 메시지마다 폐기 → 이 메시지 키가 털려도 다음 메시지는 안전
Alice의 상태 (지속 갱신)
RK (root key) ← 매 DH ratchet마다 교체
CK_send, CK_recv ← 매 메시지마다 KDF
MK_n ← 메시지 암호화 후 즉시 삭제
FS + PCS 둘 다 보장
